VisualKB / Session Origin / 2026-05-11

Why VisualKB exists, and how this fork should evolve.

VisualKB was defined in this session as an OpenKB-derived product direction: keep the LLM Wiki idea, but move the primary knowledge artifact from Markdown pages to renderable, inspectable, source-linked HTML Knowledge Objects.

Product: VisualKB Category: LLM Wiki with HTML Artifact: HTML Knowledge Object Fork: songblaq/VisualKB

TL;DR

Markdown is an excellent text format, but a knowledge base that contains charts, tables, timelines, images, code maps, citations, and visual comparisons should not collapse everything into prose. VisualKB keeps source material and LLM-compiled wiki behavior, while adding HTML as the first-class medium for understanding.

Why

The session started from a product observation: Karpathy's LLM Wiki pattern and OpenKB point in the right direction, but their default artifact is still Markdown. As AI vision and browser understanding improve, an LLM should be able to read not only text, but also the rendered structure of a knowledge page.

Markdown is text-first

It works well for headings, prose, lists, code, and links. It is weaker when the knowledge is inherently visual or relational.

Knowledge is often visual

Model comparisons, evaluation charts, timelines, diagrams, source relationships, and image annotations are clearer as visual structures.

LLMs can read screens

If models can understand images and browser-rendered HTML, the rendered view can become part of the knowledge representation.

What

VisualKB is not just an HTML export option. It is a product layer where the compiled wiki produces HTML Knowledge Objects: pages or component bundles that preserve text, visual layout, data, source links, accessibility labels, and optional screenshots.

OpenKB baseline
  • Ingest raw documents into a compiled LLM-maintained wiki.
  • Use Markdown pages and wikilinks as the durable output.
  • Keep compatibility with Obsidian and text-first workflows.
  • Support multimodal source understanding during ingestion.
VisualKB direction
  • Keep source preservation and compiled wiki behavior.
  • Add HTML Knowledge Objects as a primary output target.
  • Represent knowledge as charts, matrices, timelines, diagrams, cards, and source strips.
  • Let humans and LLMs inspect the same rendered knowledge object.

Implementation Direction

The first engineering pass should be narrow: add an HTML output path without destroying the existing Markdown wiki path. The fork should remain easy to compare against upstream OpenKB.

1. Add an HTML renderer beside the existing Markdown renderer.
2. Define an HTML Knowledge Object schema: title, TL;DR, sections, sources, visuals, data refs.
3. Add CLI target flags such as --target markdown, --target html, or --target both.
4. Add visual components for comparison matrix, timeline, source strip, chart placeholder, and concept cards.
5. Add lint checks for broken links, missing citations, missing alt text, and chart/data mismatches.
6. Keep OpenKB compatibility until VisualKB has its own clear product surface.
