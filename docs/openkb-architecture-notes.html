VisualKB Architecture Notes

OpenKB Integration Notes

OpenKB is already organized around source conversion, LLM compilation, Markdown wiki pages, query tools, and linting. VisualKB should add HTML output as a parallel rendering target first, then deepen compiler prompts and query support after the artifact path is stable.

Repository: songblaq/VisualKB Base: VectifyAI/OpenKB Updated: 2026-05-11

Observed Architecture

The current codebase has a clean pipeline that can be extended without changing source ingestion first.

CLIopenkb/cli.py

Initializes KB folders, adds files, runs queries, updates logs, and stores hashes.

Conversionopenkb/converter.py

Copies originals to raw/, converts sources into wiki/sources/, and routes long PDFs through PageIndex.

Compilationopenkb/agent/compiler.py

Prompts the LLM for summaries, concepts, backlinks, and wiki/index.md.

Schemaopenkb/schema.py

Defines AGENTS.md, page types, wiki conventions, and Markdown/wikilink expectations.

Queryopenkb/agent/query.py

Uses tools to read index, wiki pages, source files, and images for answer generation.

Toolsopenkb/agent/tools.py

Exposes read/write helpers scoped to the wiki root and supports image reading.

Lintopenkb/lint.py

Checks Markdown wiki structure: broken wikilinks, orphans, raw entries, and index sync.

Rendereropenkb/agent/_markdown.py

Renders Markdown in terminal output and already preserves inline/block HTML.

Current Output Contract

OpenKB output is Markdown-first. VisualKB can reuse this contract as an intermediate representation in the first MVP.

Extension Points

These are the practical places to add VisualKB behavior with limited blast radius.

Config target

Add targets or output_targets to .openkb/config.yaml. Start with markdown, html, and both.

HTML renderer module

Create a renderer that reads compiled Markdown/frontmatter and writes standalone HTML objects.

Compiler prompt upgrade

Later, ask the LLM for structured sections and visual component hints instead of only Markdown content.

Index builder

Generate html/index.html from summaries, concepts, briefs, tags, and sources.

HTML lint

Add checks for broken links, missing alt text, missing source strips, unresolved data refs, and mobile overflow signals.

Query read path

Allow query tools to read HTML object text/metadata while retaining the existing Markdown wiki tools.

Suggested Sequence

This order keeps the first version testable and avoids entangling ingestion, prompting, rendering, and query behavior all at once.

1. Add config support for HTML targets.
2. Add html/ directory creation during init.
3. Implement a deterministic HTML renderer from existing wiki pages.
4. Add render-html command for rebuilding without LLM calls.
5. Wire add/query save paths to call the renderer when HTML is enabled.
6. Add HTML lint checks.
7. Add browser screenshot smoke tests for generated pages.
8. Upgrade prompts to emit visual component hints after the renderer is stable.

Risks

These are the main technical risks to manage during the MVP.

Prompt drift

If prompts ask for free-form HTML too early, output quality may vary. Start with deterministic rendering.

Source ambiguity

Visual components can imply precision. Require source-backed data or clear illustrative labels.

Two outputs can diverge

Markdown and HTML need sync checks or a single source of truth for metadata.
