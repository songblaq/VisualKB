VisualKB Schema

HTML Knowledge Object Schema

An HTML Knowledge Object is the durable VisualKB artifact: a renderable page that stores text, source links, visual components, accessible descriptions, and optional backing data in one inspectable structure.

Category: LLM Wiki with HTML Artifact: Static HTML Updated: 2026-05-11

Context

OpenKB compiles raw documents into Markdown summaries and concept pages. VisualKB keeps that source-linked wiki idea, but adds an HTML artifact layer so knowledge can be read as prose, inspected as DOM, rendered as visual layout, and checked as a screenshot.

Required Fields

Every object should be useful when opened directly in a browser and when read by an LLM through raw text or DOM extraction.

FieldMeaningHTML representation
titleHuman-readable object name.<title>, <h1>, and optional JSON metadata.
tldrOne-paragraph summary that preserves the origin idea.Lead paragraph near the top of the page.
object_typeConcept, summary, comparison, data, code, image, architecture, or exploration.Visible metadata chip and machine-readable metadata.
sourcesSource files, URLs, local paths, or generated-source notes.Source strip with links, labels, retrieval date, and source type.
sectionsStructured body content.Semantic <section> blocks with stable anchors.
visualsKnowledge components such as charts, matrices, timelines, diagrams, and figure callouts.Tables, SVG, HTML/CSS components, or data-backed charts.
data_refsBacking CSV/JSON for charts and tables.Relative links to html/data/ or KB-level data/.
accessibility_textText equivalent for visual structures.aria-label, captions, table headers, alt text, and visible summaries.
updated_atLast compile or manual update date.Footer and JSON metadata.

Object Types

The compiler should choose an object type based on the knowledge task, not on the visual style alone.

concept-page

A durable explanation of one idea, similar to an OpenKB concept page but with visual structure.

summary-page

A source-specific digest of one document, equivalent to summaries with source cards and figures.

comparison-page

Alternatives, models, libraries, APIs, products, or decisions compared in a matrix.

data-page

CSV/JSON-heavy material with charts, tables, and backing data references.

code-page

Repository architecture, call flow, module map, implementation notes, or API contracts.

image-page

Screenshots, diagrams, figures, annotated images, and multimodal evidence.

File Layout

For the MVP, the HTML layer should sit beside the existing Markdown wiki. This keeps OpenKB compatibility while making VisualKB output easy to test.

kb-root/
|-- raw/
|-- wiki/
|   |-- sources/
|   |-- summaries/
|   |-- concepts/
|   `-- index.md
|-- html/
|   |-- index.html
|   |-- summaries/
|   |-- concepts/
|   |-- explorations/
|   |-- assets/
|   `-- data/
`-- .openkb/

Component Contract

Visual elements should carry knowledge, not decoration. Each component needs a plain-language equivalent so the object remains readable without pixels.

HTML Knowledge Object
TL;DR

Origin and purpose in one paragraph.

Source Strip

Local files, URLs, and inference markers.

Visual Component

Matrix, timeline, chart, or map.

Open Questions

Limits, missing sources, and decisions.

<article class="knowledge-object" data-object-type="concept-page">
  <header>
    <h1>VisualKB</h1>
    <p class="tldr">...</p>
  </header>
  <section id="sources" aria-label="Sources">...</section>
  <section id="visual-model" aria-label="Visual model">...</section>
  <script type="application/json" data-visualkb-schema>{ ... }</script>
</article>

Validation Rules

HTML objects need a lint path separate from Markdown wikilink checks.

Source integrity

Every factual section should link to sources or be explicitly marked as inference.

Path integrity

Local links, image paths, CSS assets, and data references must resolve.

Visual integrity

Charts and tables must match their backing data or state that they are illustrative.

Accessibility

Images and visual components need alt text, labels, captions, or text summaries.

Responsive layout

No overlapping text, clipped headings, or horizontal overflow on mobile.

LLM readability

The page should be useful through raw text and DOM inspection, not only as pixels.
